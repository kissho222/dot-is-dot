# dot / Codex / GitHub 運用ルール v0.2

**所有者・dot・Codexの並行作業に関する実施規則は [WORK_COORDINATION.md](WORK_COORDINATION.md) を参照する。** 当文書の一般的な権限・安全ルールと合わせて守る。

## 1. 正本と管理範囲

- **dot-is-dot** は全案件横断の引き継ぎ、優先順位、成果記録、管理運用の拠点。
- **各ゲームのリポジトリ** はゲームコードとゲーム固有の仕様・実装Issueの正本。
- **Googleスプレッドシート** は将来のWarrior Cats翻訳本文・担当・レビュー管理の候補。現在作成済みとはみなさない。
- **Discord** はWarrior Cats翻訳チームの既存の連絡拠点。
- 重大な仕様変更を決めたら、Issueのコメントで埋もれさせず、恒久Docsにも反映する。

## 2. dotの最初の実行手順

1. HANDOFFとBACKLOGを読む。
2. アクセス可能なプロジェクトのリポジトリ・Docs・Issue・PRを照合する。
3. 以前に完了したタスクと重複している候補を除外する。
4. 「着手可能」「仕様待ち」「環境待ち」「調査待ち」「完了」「対象外」に仕分ける。
5. 実作業へ進めるものから小さく着手する。成果物・検証結果・次工程を残す。
6. 10月24日以降はWarrior Cats日本語化の技術調査へ配分を優先的に移す。

## 3. IssueとCodex

- ユーザーが「タスク作成して」と言った場合は、対象リポジトリに**GitHub Issueを実際に作成**する運用。
- **Codexへ指示するIssueには必ず codex-task ラベルを付ける。**
- 人間向けの翻訳依頼、単なる調査メモ、dotだけが担当する仕事に機械的にcodex-taskを付けない。
- 実装タスクは dot-is-dot にコードを置くのでなく、対象ゲームのリポジトリへ作るのが基本。
- Codexの利用枠・費用・実行開始条件は別管理。**Issue作成はCodex実行の成功を意味しない。** ラベル付与が自動実行につながる構成であれば実際の影響を事前に確認する。
- **所有者が在席中、dotからCodexへ新規タスクを指示・起動することは所有者の明示指示がある場合だけ**。離席中も委任済み範囲内に限る。状態不明なら新規の起動は保留する。
- 実装結果はPR/差分・テスト結果で確認する。未確認のものを「完了」と断言しない。

### Issueの推奨書式

- **背景**：何が問題／必要か。元になる仕様書やIssueのリンク。
- **目的**：到達させたい状態。
- **対象**：リポジトリ、Scene、対象コンポーネント、データ等。
- **依存関係**：前提となるタスクや承認。
- **作業内容**：実装／調査の範囲と、明示的に行わないこと。
- **受入条件**：チェック可能な完了条件。
- **検証**：どの環境でどう試し、何を報告するか。
- **リスク**：破壊的変更、互換性、権限、性能、著作権。

### 推奨ステータス

Proposed（候補） / Ready（実行準備完了） / In Progress（作業中） / Blocked（停止中） / Needs Review（確認待ち） / Done（確認済み）。

Review待ちとDoneは同じではない。確認した結果に基づき更新する。

## 4. 安全と承認の境界

### 事前承認なしで進めてよいものの例

- 公開情報の調査、既存コード・仕様の読解、Issueの棚卸し。
- 草案の作成、既存Issueのレビュー用整理、非破壊の検証。
- 明示された制作仕様に沿う小規模な成果物の試作。
- 進捗レポートと次の作業の提案。

### 原則として所有者に承認を求めるもの

- 作品の主要な仕様変更、キャラクターや世界観の大きな改変。
- 既存データの削除、強制Push、重要ブランチへのマージ、実運用への公開。
- 費用が発生するサービス・アセット・サブスクリプション購入。
- 外部相手へのメール送信、第三者への共有、ゲーム・翻訳MODの一般公開。
- 権利処理が曖昧な第三者ゲームのファイルや抽出データの共有。
- 複数の自動作業を大規模に同時起動し、利用枠やリポジトリを圧迫する操作。
- 所有者またはCodexが使用中の同一Unity Editor／Scene／Prefab／通常セーブデータ／作業ツリーの共有操作。衝突する場合は [WORK_COORDINATION.md](WORK_COORDINATION.md) に従い、安全なチェックポイントを作って譲る。

認証情報、個人情報、私的な契約、チーム員の個人情報は公開リポジトリへ書き込まない。

## 5. 3Dモデル制作の流れ

1. **制作対象の個別オーダーを取得**。形状・寸法・材質・ギミックなどの未確定項目を明確にする。
2. 既存アセットとの重複を確認する。
3. 単体モデルを制作し、編集可能な元データとUnityへの取り込み形式を用意する。
4. スケール、原点、テクスチャ・マテリアル、ポリゴン数、可動部、ライセンス、取り込み時の表示を確認する。
5. 作品のスケール（プレイヤー約5cm）と至近距離からの見え方を確認する。
6. 所有者のレビューを経て完成とし、得た知見を次の小物制作へ反映する。

ブレンダー上で見た目ができたことと、Unityのゲームで使えることは別。**未検証は未検証と記録する。**

## 6. Warrior Cats翻訳プロジェクトの流れ

1. 発売後、正当に入手・参照できる実データを調査。
2. 技術成立性、日本語表示、抽出・差し戻し、配布条件を確認。
3. 最小サンプルをゲームへ反映し、成否を報告。
4. 分量・カテゴリ・難度・文脈情報を整理して作業単位へ分割。
5. 翻訳者3名・アシスト3名の適性に合わせた分担を提案し、所有者の承認を得る。
6. Discordで依頼・質問、スプレッドシートで本文・担当・校正、GitHubでツールと技術課題を管理。
7. QAを実施し、更新による差分に対応する。

翻訳者にGitHubの知識を要求しない。翻訳文の取り扱いはゲーム開発元の権利・利用規約と整合させる。許可されない第三者データは公開しない。

## 8. 例外と保留

- 各ゲームの仕様や作業状況が矛盾したら、独断で決めずに根拠と選択肢を示す。
- 作業環境が使えない場合、「できたこと」「できなかったこと」を分け、無理に成功と報告しない。
- 作業枠の都合でCodexが動かない場合、調査・タスク整備・資料化など独立した仕事を先行できる。ただしdot側にも固有の利用上限があり得る。
- **所有者が在席に戻ったら主導権を所有者へ戻すが、dot自身の競合しない仕事は続けてよい。** 在席状態は明示指示を使う。仕事の競合はA/B/Cの3区分で確認し、疑わしい場合は共有環境の使用を保留。
- 予定・価格・Pro/dotの利用条件は変わり得るため、必要なときに公式情報で再確認する。
