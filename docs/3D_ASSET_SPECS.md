# NEKOLPOS 3D小物 — 共通・個別制作仕様 v0.2（2026-10-14）

## 状態と参照画像

- この文書は所有者の**確定指示**を含む、dot向け3D制作仕様。
- チャットで共有された2枚の画像を参考とする。**画像ファイルそのものはこの公開リポジトリに含めない**。dotには制作開始時に画像を直接渡すこと。画像未取得時はその旨を報告する。
- 給餌器は画像1枚目の**右側の白い機種**を主な外観参考にする。給水器は画像2枚目の**右側の白い機種を外観参考**にし、**左上の別カットを湧出・水流構造の参考**にする。
- ブランド名、ロゴ、広告文言の再現は必要ない。外観の雰囲気と構造を参考に、ゲーム向けの独自モデルとして制作する。

## 1. 全NEKOLPOS 3Dに共通する原則（確定）

### 見た目と性能

1. プレイヤーは身長約5cmの小人。**ほとんどのObjectに至近距離まで接近できる**ので、近くで見たときの厚み、縁、面のつなぎ目、穴の奥行き、使用感が破綻しないこと。
2. **極端なハイポリ化はしない**。滑らかに見える必要のある部分は必要十分な分割を使い、細部はノーマル／ラフネス／汚れ等のマテリアル表現を併用する。
3. **ほとんどの小物は新品ではなく、自然に経年使用した見た目**にする。微細な擦れ、くすみ、細かい傷、埃が溜まる溝などを適度に配置する。生活用品としての清潔感は保ち、極端な破損・汚染は不要。
4. 近づける、乗れる、内部に入れる対象では、**外観メッシュとゲームプレイ用の空間・部品を後から調整できる構成**にする。プレイヤー移動を妨げる偽の黒い穴や、塞がったままの水槽のような形状は不可。
5. Unityでの描画・当たり判定の負荷を優先し、全てのカリカリ等を個別GameObjectで保持する必要はない。描画用のまとまりと、触れる・拾える少数の実体を区別できるようにする。

### 今回の作業範囲

- **第一段階は外観モデルと将来ギミックに対応できるメッシュ構造を作る段階**。
- Blender等の編集可能な元データ（.blendなど）とUnity向けモデル（.fbx等）、マテリアル／テクスチャ、全周・接近プレビューを納める。
- 給餌器の餌の増減・給水器の水流は**表示のために仕込める構造**を作る。必要なら最小限の表示用の動作確認を追加するが、実際のゲーム内のタイマー、残量計算、詰まりイベント、ポンプ、飲水判定、物理流体シミュレーションは別タスクとする。
- 給水器の**「常に水が流れて見えること」自体は必須の見た目要件**。まずは簡単な流れの視覚表現を提案・検証する（例：別メッシュの水面＋UVスクロール／簡易ループ）。物理シミュレーションは不要。
- 各モデルの部品名・原点・スケールを整理し、Unityで部位別に差し替えや調整ができる構造にする。
- 先にラフを1点作り、所有者のレビューを経て詳細へ進む。全対象を一度に完成扱いしない。

## 2. 3D-01 自動給餌器（電動・白）

### 外観（確定）

- **電動式・白色**を採用。画像1枚目の白い機種が主参考。黒色版の同時制作は求めない。
- 縦長の角丸箱形タンク、上下の本体の継ぎ目、正面表示窓／操作部、下部給餌口、手前の浅い金属製丸皿。
- 軽い擦り傷、角やボタン周辺のくすみ、細い合わせ目など、日常使用の経年感をつける。
- お皿は本体から独立させて制作・調整できる形が望ましい。

### タンクの餌残量表示（構造が必要）

- 設定上、**補充は週1回**。
- タンクの中に見える餌を、**餌のテクスチャを貼った内部メッシュ／面などを少しずつ下げていく方法**で減少表現できる構造にする。
- 本体の外側から残量が認識できる透明・半透明の窓などが必要かは、参考画像とラフを見ながら決める。中身が全く視認できない設計にはしない。
- 個々のフード粒の落下や内部での物理計算は不要。残量表示用メッシュを部品として独立させ、上下移動で見た目が変わることを確認できる状態を目標とする。
- **実際の週ごとの補充処理・残量計算の実装は今回不要**。

### 給餌口：将来侵入できる横穴（必須）

- 下部の給餌口は**黒く塗った平面や浅いくぼみでは不可**。入口から内部方向へ続く**実際の横穴・空洞**を作る。
- 将来「小人プレイヤーが中に入って、奥の詰まりを解消するイベント」を予定。入口、床・側壁・天井、奥行きと通路の見え方を形状で作る。
- 最初のモデル段階でイベントや内部の完全な機械は制作しないが、**将来プレイヤー用の当たり判定／カメラを置ける空間を塞がない**。
- 通路の内寸はプレイヤー身長約5cmだけで決めず、実際のキャラクターの幅、Collider、カメラNear Clip等をUnityプロジェクトで確認して調整する。未確認の場合は寸法確定を保留し、仮の通路サイズを明記する。
- 将来の詰まりオブジェクトを追加できるよう内部を部品として管理する。

### 皿のカリカリ

- **1粒単位で持ち上げられる粒が必要**。
- ただし全粒を個別Object化する必要はなく、**まとまりメッシュ／描画用群＋少数の拾える個別粒**を併用してよい。
- 皿、本体、カリカリのまとまり、拾えるカリカリを別部品として用意する。実際の拾う操作・物理・インベントリ処理は後工程。
- 最優先はゲームの快適な動作と近距離の見た目の両立。

### 今回の非対象

給餌タイマー、ボタン操作、実際の餌排出、残量ロジック、詰まり解消イベントの進行処理、各粒の完全な物理挙動。

## 3. 3D-02 自動給水器（電動・水道直結）

### 外観・給水構造（確定）

- **電動式で水道管・給水ラインへ直接接続するタイプ**として扱う。給水を追加補充するタンク型ではない。
- **外観は画像2枚目右側の白い給水器**。低く丸い円筒形の白系本体、広い飲水エリア、中央の盛り上がりを基本とする。
- **湧き出て周囲へ流れる構造は画像2枚目左側の別カット**を参考にする。水がどこから出て、どのように皿へ広がるかが幾何形状として読み取れるようにする。
- 水道直結を示す接続口やホース取り回しの余地を背面・底面に持たせる。実際の屋内配管との接続・給水制御は今回不要。
- 本体は白系樹脂の使用感を持たせる。ただし給水器なので過度な汚れ・ぬめりを強調しない。

### 常時水流の視覚表現（必須）

- 高度な流体シミュレーションや美麗な水表現は不要。
- **常に水が流れているとわかる描写**が必要。水流経路に合わせて、水面、水が出る部分、流れを示す半透明メッシュ等を分割する。
- Blenderで静止メッシュを作るだけなら、Unity側で簡易ループ（UVオフセット、シンプルなシェーダー、連続した流れのアニメ等）を当てられる材質／UV構造にする。作業環境が可能なら、**簡易な常時流れプレビュー**も成果物にする。
- 物理流体や実際のポンプ・水量シミュレーション、飲水イベントはこのフェーズでは作らない。

### プレイヤーの登攀・入水（必須の形状上の前提）

- 将来、小人プレイヤーが本体の**上に登る**、水受けに**入る**予定。
- フチの厚み、上面の足場、水受けの深さ・内壁・底面、噴出口の斜面を小人視点で成立する形状にする。
- 水面を当たり判定一枚で固めたり、上面全体を塞いだりしない。将来的に**水の内側と固体部分の当たり判定を分離**できるメッシュ構成を目指す。
- 現段階では登攀操作・水中移動・泳ぎ・水によるダメージなどのゲームシステムは不要。
- 具体的な移動方法・水深・内部への入り方は既存プレイヤーColliderと移動仕様を確認し、必要なら所有者へ提案して決める。

## 4. 制作・レビュー手順

1. **dotへ元の参考画像2枚を直接共有**する（GitHubの公開リポジトリには複製しない）。
2. この仕様とBlender／Unityの現環境を確認し、欠けている情報と仮置きの寸法を区別する。
3. 2つのモデルは**別々のIssue**として実施。まず各1点のラフを作り、全周と小人視点の近接プレビューを提出する。
4. 給餌器は「入口が実際に空いている横穴」「餌残量表示用の可動メッシュ」「拾える粒を分離できること」を目視と構造で検証。
5. 給水器は「水の通り道」「常時流れて見える簡易表現」「登れる／入れる形」「水面と固体部品の分離」を確認。
6. レビュー承認後に編集可能な元データ、Unity向けモデル、マテリアル／テクスチャ、近接プレビュー、必要な作業メモを納品する。
7. Unityでの取り込み・近接表示・必要な通路／空間の成立を可能な範囲で検証し、**実施した検証と未実施の検証を分けて報告**する。

## 5. 未確定・別途確認する項目

- 具体的なスケールと配置位置。自然な猫用品の寸法から試作できるが、厳密値はレビュー待ち。
- プレイヤーの実際の幅・移動用Collider寸法・Camera設定に対する給餌口通路の必要内寸。
- 給餌器の餌が見える窓や透明部の形、残量変化の表示方法の細部。
- 水受けの水深、登攀可能な段差、Unityでの水流プレビューの実装方法。
- 各モデルの細部の装飾と傷表現の度合い。
- 最終的なポリゴン予算・LOD・UV・シェーダー・コライダー規格。

以上は合理的な仮値を使ってラフを提示し、重要な箇所から所有者が確認する。未決事項を独断で「仕様確定」としない。
